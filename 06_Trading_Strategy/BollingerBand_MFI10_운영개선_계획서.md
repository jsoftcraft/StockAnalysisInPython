# BollingerBand MFI10 운영·개선 계획서

- 작성일: 2026-10-21
- 대상: [BollingerBand_MFI10_Trader.py](./BollingerBand_MFI10_Trader.py)
- 범위: 완료 일봉 최신성 확보, 누락 일봉 자동 보충, 미매수 원인 진단
- 상태: 코드 반영 및 테스트 완료 / 다음 실거래 실행의 운영 확인 대기

## 1. 배경과 목표

2026-10-21 조사에서 Trader가 LIVE 모드로 실행되고 정상 종료했으며,
정규장 매수 평가 1,370회 모두 매수 신호가 0건인 사실을 확인했다.
당시 선정된 삼성SDI·코웨이·동서의 MFI10은 각각 58.06·75.63·63.16으로,
매수 기준인 50 이하를 충족하지 않았다.

별도로 아침 로그의 MFI10·%B·MFI 3일 변화량을 과거 일봉 재계산값과 대조하니,
100개 후보 중 70개는 10월 20일, 30개는 10월 16일 기준 값과 일치했다.
이 날짜 구성을 재현한 결과 실제 로그와 같은 3종목이 선정됐다.
이는 오래된 지표 사용의 강한 근거이나, 당시 DB 원본 스냅샷이 아니므로
전날 수집이 불완전해진 원인까지 확정한 것은 아니다.

목표는 매수 횟수를 늘리는 것이 아니라 다음을 보장하는 것이다.

1. 불완전한 일봉으로 신규 매수하지 않는다.
2. 누락 일봉을 CREON으로 직접 보충하고 완료 여부를 확인한다.
3. 데이터 복구 후 지표·선정 결과를 재평가한다.
4. 미매수 이유를 로그만으로 추적할 수 있게 한다.
5. 기존 보유 포지션과 매도 감시·주문 안전장치를 보존한다.

## 2. 유지할 전략과 안전 원칙

- MFI10 50 이하 및 현재가 > MA20이라는 매수 기준을 변경하지 않는다.
- 기존 매도 조건, 트레일링 스탑, 종목별 예산 및 주문·체결 확인 절차를 유지한다.
- 지표는 오늘 이전의 완료 일봉으로 계산한다. 장중 틱마다 MFI를 재계산하지 않는다.
- 보충은 누락 행 삽입만 수행하며 기존 DB 가격을 덮어쓰지 않는다.
- 최신성 오류가 발생하면 신규 매수를 차단한다. 데이터 오류를 매수 허용으로 대체하지 않는다.
- 데이터 오류가 있어도 보유 종목의 매도·트레일링 스탑 판단 경로는 유지한다.
  다만 API 연결·DB·시세 조회 자체의 장애가 있어도 매도가 반드시 실행된다는 의미는 아니다.
- 당일 매도 후 재진입 금지, 계좌/관리 수량 검증, MFI/DayTrading 소유권 분리를 유지한다.

### 3.1 적용 모드

| 실행 모드 | 이번 자동 일봉 수집·저장 기능 |
|---|---|
| 일반 `--live --confirm LIVE` | 활성화 |
| 모의 실행 | 비활성화 |
| `--monitor-only` | 비활성화 |
| `--daytrading-monitor-only` | 비활성화 |
| 읽기 전용 대시보드 | 비활성화 |

이 표는 신규 자동 일봉 수집·저장 기능의 적용 범위이다.
감시 전용 LIVE 모드의 기존 포지션 상태 저장 등 다른 DB 쓰기를 금지한다는 의미는 아니다.

### 3.2 처리 주기와 부하 제한

- 최신성 확인 및 실패 재시도 주기: 300초.
- 한 감시 주기의 보충 상한: 3종목.
- 보충 대기 종목은 다음 감시 주기에 이어서 처리한다.
- 주말·휴장일을 평일 계산으로 추정하지 않고 기준 종목의 실제 일봉 날짜를 사용한다.
- 이력이 64개 이상인 종목은 조회 구간 내 최초 저장일부터 누락을 검사한다.
  이력이 부족하거나 없는 종목은 기준 거래일 목록의 시작일부터 보충을 시도한다.
- 거래정지·신규상장 등으로 기준 날짜의 일봉이 없으면 보충이 불완전할 수 있으며,
  이를 정상 완료로 처리하지 않는다.
- 수집은 감시 루프 안에서 동기 실행된다. 3종목 제한은 처리량 상한이지
  실행시간 상한이 아니며, API 제한 대기·DB 저장·선정 재계산만큼 감시가 지연될 수 있다.

## 4. 실행 흐름과 장애 처리

1. 일반 LIVE 감시 루프에서 CREON 완료 거래일과 DB 보유 일봉을 확인한다.
2. 확인 실패 시 전체 신규 매수를 차단하고 오류를 기록한다.
3. 누락이 있는 종목을 대기열에 넣고 주기당 최대 3개씩 수집한다.
4. 오늘/미래 일봉을 제외하고 날짜·중복·수치·OHLC 범위를 검사한다.
5. 누락 행만 저장하고 DB를 다시 조회해 실제 복구 여부를 확인한다.
6. 실패/미완료 종목은 해당 상태를 기록하고 다음 최신성 확인에서 재시도한다.
7. DB를 새로 읽어 데이터 품질과 선정 조건을 평가한다.
8. 정상 데이터와 기존 전략 조건을 모두 통과한 종목만 매수 판단을 진행한다.
9. 보유 포지션은 기존 매도 감시 경로로 처리한다.

기준 거래일/DB 최신성 확인 실패 또는 보충 후 지표 재조회 실패는
전체 신규 매수 차단 사유이다. 개별 종목의 데이터 품질 문제는 해당 종목을 차단한다.
한 종목의 보충 성공이 전체 후보의 보충 완료를 의미하지 않으며,
`[일봉 보충 완료]` 자체도 매수 신호나 주문 체결을 의미하지 않는다.

## 5. 진단 로그 계획

기본 MFI 로그 위치: `%LOCALAPPDATA%\StockAnalysisInPython\logs\trader.log`

| 로그 표식 | 확인할 내용 |
|---|---|
| `[일봉 최신성 확인]` | CREON 기준 완료일, 확인 대상 수, 보충 대기 수 |
| `[일봉 보충 대기]` | 종목별 DB 최근일, 기준일, 누락 거래일 수 |
| `[일봉 보충 완료]` | 종목별 보충 구간, 신규 삽입 행 수 |
| `[일봉 보충 미완료]` | 저장 후에도 남은 누락과 매수 차단 유지 |
| `[일봉 보충 실패]` | 수집/저장 실패 원인과 재시도 예정 |
| `[일봉 갱신 오류]` | 기준일 확인 또는 지표 재조회 실패와 전체 신규 매수 차단 |
| `[일봉 지표 갱신]` | 후보/지표 변경에 따른 재평가 |
| `[종목 선정 진단]` | 일봉 날짜, 기준일, 이력 수, 실제 선정 필터 불충족 사유 |
| `[매수 판단 상세]` | 선정/보유 종목의 현재가·MA20·MFI10·보유 수량·차단 사유 |
| `[매수/매도 조건 조회]` | 정규장/애프터마켓 조회 상태, 신규 매수 허용/차단 상태 |
| `[매수조건 확인]` | 평가 종목 수와 매수 신호 수 |

- 선정 진단은 후보 요약 출력 시 기록한다.
- 매수 상세는 첫 판단, 판단 상태 변경, 300초 경과 시 기록한다.
  가격이 매 틱 바뀌는 것만으로 상세 로그를 반복하지 않는다.
- 조회 대상이 0개여도 세션 변경 또는 300초 경과 시 상태를 기록한다.
- 매수 신호 이후 주문 가능 수량이 없으면 예산·호가·비용 여유율도 기록한다.
- 모니터의 최근 이벤트에는 일봉 관련 표식을 포함한다.

  DayTrading 별도 예산, MFI10 50 이하, 선정·트레일링 스탑 조건은 유지.

- 실제 읽기 전용 CREON 요청에서 `A0167A0`, 가격 16,025원 응답을 확인.
  단독 COM 검증 프로세스는 응답 출력 후 네이티브 종료 오류가 발생했으므로
  해당 실행 전체를 정상 종료 검증으로 간주하지 않음.
  변경 코드를 가져오지 않는 삼성전자 직접 조회에서도 같은 종료 코드가 재현되어
  코드 변환 수정과 분리함. 다음 운영 확인 시 COM 종료도 별도 확인.

### 6.3 다음 일반 LIVE 실행의 운영 확인 항목

- [ ] 예약 작업이 올바른 배치 경로·인터프리터·관리자 권한으로 실행되는지 확인.
- [ ] 개장 후 첫 감시에서 CREON 기준일과 후보별 일봉 날짜가 기록되는지 확인.
- [ ] 실제 누락이 있으면 대기 → 보충 → DB 재조회 → 재평가 흐름이 기록되는지 확인.
- [ ] 남은 누락/실패 종목은 매수 차단 상태이며 정상 완료로 표시되지 않는지 확인.
- [ ] 선정 종목의 미매수 이유가 현재가·MA20·MFI10 및 차단 사유로 설명되는지 확인.
- [ ] 시작 로그의 종목별 한도가 2,000,000원인지 확인.
- [ ] 영문 혼합 코드 시세가 정상이고, 잔여 한도 부족 시 반복 매수 신호가 없는지 확인.
- [ ] 모니터의 실제 판단 기록 시각과 차단 사유가 현재 실행 로그와 일치하는지 확인.
- [ ] 보유 종목 감시 주기의 실제 지연과 API 제한 대기 시간을 확인.
- [ ] 애프터마켓 및 조회 대상 0종목 상태에서도 로그가 이어지는지 확인.
- [ ] 당일 종료 후 정상 종료 기록과 예약 작업 결과를 대조.

운영 확인 목적으로 매수를 강제하거나 매수 기준을 완화하지 않는다.
검증되지 않은 실주문을 추가로 실행하지 않는다.

## 7. 후속 개선 과제: 미구현/별도 승인 범위

| 우선순위 | 과제 | 완료 판단 기준 |
|---|---|---|
| 높음 | 전날 전체 일봉 수집의 지연/누락 원인 추적 | 수집 시작·완료·실패와 후보 변경 시점을 대조해 누락 원인 확인 |
| 높음 | 예약 작업 경로 점검 | 조사 당시 저장된 OneDrive 바탕화면 경로와 실제 배치 위치 차이를 확인하고 유효 경로 검증 |
| 중간 | 수집 중 감시 지연 계측 | 조회·보충·재선정 시간을 분리 측정한 뒤 필요 시 처리량/실행 구조 조정안 결정 |
| 중간 | 거래정지/신규상장 반복 보충 정책 | 실제 상장·거래정지 정보로 수집 불가능 사유 구분, 매수 안전성 유지 여부 검증 |
| 중간 | 기준 거래일의 독립 검증 | 단일 기준 종목 API 응답 자체의 지연/누락을 탐지할 교차 검증 방식 결정 |

위 항목은 이번에 구현 완료한 기능과 구분한다.
시간 상한, 별도 수집 프로세스, 휴장일 전용 데이터, 상장/거래정지 예외 처리는
구현된 기능으로 간주하지 않는다.
